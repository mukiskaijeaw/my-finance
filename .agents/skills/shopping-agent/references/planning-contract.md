# Adaptive planning contract (local, version 1)

Python standard library only. Extend existing profile contract; do not migrate the user's profile or ledger. `shopping.py plan --format markdown` receives JSON on stdin. Codex extracts intent/confirmed inputs, invokes Python, then presents the returned Markdown. Users never need to write JSON. `evaluate` can also contain `planning`; product cards then use cycle-aware fit. Explicit `include_financial:false` never loads or exposes planning data.

## Observed providers

Inspect the selected local provider before use. The adapter accepts exact 14-column and legacy 11-column transaction schemas without merging records; totals are not bank balances. Unknown or unconfirmed profile values remain unknown. Tax worksheets and historical recurring payments are not automatically confirmed payable schedules. Accept future commitments only from confirmed local provider/user data.

## Common request

`{"profile":{...existing confirmed fields...},"planning":{"action":"budget","budget":{...}}}`

`--finance-dir` and optional profile_path use the existing adapter. No implicit default provider; choose only the user-authorized local provider. Fresh reads on every request. Legacy profile remains unsupported. No change to CSV or other pillars. Missing values remain null, never zero. Amounts use Decimal strings, dates Gregorian ISO, Bangkok runtime date.

### budget options (required for every action)

- `cycle_complete:true`: user confirms the outstanding cycle is complete, including overdue bills.
- `next_income_date`: confirmed next receipt, > today and <=93 days away. No new income is credited before this day; same-day obligations reserved first. Uncertain freelancers must confirm a conservative receipt date or get INSUFFICIENT_DATA. Base variable-income calculation also requires >=3 complete months and uses the minimum.
- `minimum_remaining`: exact user-confirmed additional free-cash buffer, including explicit "0" if none. No inferred percentage.
- `user_budget`: optional/null; retain original budget. Recommended=min(user_budget if provided, affordable minus buffer). Report a conflict without silently changing the requested budget. Search matching products in recommended range first, then original range, filter locally.
- `obligations`: explicit [] or array of `{id,due,amount,certainty:"confirmed",state:"paid"|"unpaid",covered_by:"none"|"reserved"|"future_extra"}`. IDs identify distinct liabilities; never put the same bill under two IDs. Dates through next_income_date only; later extras use existing future_extra. Paid bills are not deducted. Future dates marked paid are rejected (prepayment can be represented using its actual payment date). Covered bills validate aggregate coverage and are not deducted twice. User/adapter must reconcile bill IDs with transaction references; the engine does not guess which transaction paid a bill.

Available=cash-emergency-reserved-all future_extra-uncovered unpaid obligations. affordable=max(0,available) only if monthly surplus>=0; recommended additionally protects minimum_remaining. Financial Fit invokes the existing engine with only additional reserves added. Legacy future_extra remains a conservative all-future reserve, not a day-by-day forecast. No income inferred from transactions.

### actions and outputs

- `budget`: returns three separate budgets, conflict/difference, balances, obligations, cycle_end, assumptions.
- `fit`: additionally `price` (verified effective price, not estimate), returns existing four statuses/ETA/progress and budget. For product lists use `evaluate` with verified listings so price evidence is validated automatically. Standalone price must come from verified effective-price output or user-confirmed final checkout total.
- `opportunity`: additionally price and `opportunity:{confirmed:true,free_cash_used,goals:[{id,target,saved,monthly_contribution,purchase_draw,monthly_diversion,approved_change}]}`. All goal savings are protected slices of reserved cash, total monthly contributions <= saving; free_cash + draws must equal purchase price. Zero draws/diversions give zero delay. Any draw/diversion requires explicit permission to simulate that trade-off. Never assumes permission to actually change a goal. Draw cannot exceed savings. Monthly diversion is an indefinite hypothetical reduction of goal contributions, not extra income; cashflow is unchanged because allocation stays in the savings flow. Outputs before/after ETA, delay, savings reduction, immediate and monthly cashflow changes. No returns assumed. None ETA means cannot reach under stated contribution; never display it as zero months. Emergency cash cannot be used.
- `installment`: price plus `installment:{verified:true,checked,source,down_payment,periods,payments:[...],interest_total,fees,total_payable,cashflows_complete:true,cashflows:[{month:"YYYY-MM",income,outflow,pre_income_outflow,protected_floor}]}`. Terms verified from actual HTTPS offer <=7 days. payments includes principal+interest; fees paid upfront only, not again inside payments. Require down+sum(payments)=price+interest and total_payable=down+sum(payments)+fees. Flows cover consecutive months starting next_income_date's month, through entire term (1..120). outflow includes existing debts, essentials, savings, current unpaid bills and future extras exactly once; excludes new installment and upfront fees/down. pre_income_outflow is the subset due before income and includes current cycle obligations in the first month. Monthly payment is conservatively before income. protected_floor is the user-confirmed remaining protected balance after bills paid, at least emergency+minimum buffer; includes existing goal balances. Outflows/floors are explicit scenario input, not inferred from ledger. Returns full cashflow schedule, cash-fit, totals, additional cost. Any negative monthly remainder or breach of floor => NOT_AFFORDABLE; 0% alone is not a recommendation.
- `what_if`: `scenario:{changes:{...},prices:[...]}` copies actual profile. Allow only income,essential,debt,saving,cash,earmarked,future_extra,income_history; never override date/completeness/security flags. Basket sums verified prices once. Returns actual/hypothetical calculations and changed fields; writes nothing. For dated bills change confirmed future_extra or prepare a separate explicit budget scenario, never alter actual source. Variable-income raises must update hypothetical history explicitly too, otherwise historical minimum still applies.
- `readiness`: `goals:[{id,allocated_savings,allocation_confirmed:true,planned_monthly_contribution,latest_listing}]`. Read stored goals locally, fetch fresh listings externally using product attributes only, then supply newly verified latest_listing to this action. Summed allocations <=recommended budget and contributions <=monthly surplus, protecting against shared cash double-counting. Include every active goal from the canonical latest snapshot, not only the one being asked about. Planned contribution is not actual allocated cash. Returns latest effective prices, gaps, ETA in months, status and checked date. Stored target price is a preference, never a live offer. No automated forecasting of receipt dates from month count.

Readiness also returns estimated_purchase_date: today if ready, otherwise assumes monthly contributions on the confirmed next_income_date day (clamped to month end). Dates after the next receipt are hypothetical, not promised income dates. Very distant dates beyond year 9999 remain null.

All functions return status, issues and assumptions when calculable. Missing/contradictory input => INSUFFICIENT_DATA. The Python engine validates consistency, not the truth of user confirmations or retailer evidence.

## Consent-only goal snapshots

`shopping.py goal --consent --output <shopping-agent/local/new-version.json>` with readiness payload; each goal also needs product_name,target_price. Validates all allocations and fresh prices first. Exclusive creation, no overwrite; updates create a new explicitly approved snapshot. Stored fields include product name/URL, target/latest verified price, allocated savings, planned contribution, estimated purchase months, fit status, checked date. Snapshot contains only goals, not profile/transactions. Agent uses latest approved snapshot as canonical and supersedes previous versions, never adds balances across snapshots. Do not include private data in filenames. Without consent do not write. Re-evaluation alone never modifies snapshots. local/ must remain ignored. No background jobs, cart actions or transactions.

## Chat routing and templates

No fixed natural-language parser: Codex selects intent and constructs typed requests from evidence. Recommendation without a budget -> offer smart budget; do not force finances for price-only requests. Affordability -> budget+fit; relevant existing goal -> opportunity; installments -> payment comparison; changed assumptions -> what_if; saved item -> fresh readiness. Separate invocations can compose actions while reusing confirmed input. Each action has a Markdown card in planning_cards.py. Show only relevant cards. Numbers come from engine; user sees concise Thai explanation of missing fields rather than raw JSON. No HTML, server or separate UI.

Financial processing scripts run locally and make no network calls. Codex chat is not an offline model runtime; never claim otherwise. Do not send raw CSV/slips/profile into external search, APIs or product queries. Show only task-relevant computed financial summaries in the conversation.
